# Persist Worker Facts, not Worker Observations

ADR-0046 supersedes this decision's references to a fatal Workspace-global Work Journal; Worker Facts now enter their owning Graph's Work Graph Fact stream.

Coda separates Worker Runtime output into three closed algebras with different ordering semantics. A Worker Fact is bounded orchestration data admitted to the fatal Work Journal barrier. A Worker Observation is best-effort presentation data published through a bounded, non-throwing path. A Worker Control event is the semantic subset that may causally submit Work Item Input and is invoked only after all applicable Session and Work Journal barriers have succeeded. One generic `WorkerRuntimeEvent` must not cross all three seams.

The Work Journal stores a closed Worker Fact union rather than serialized Agent events. Facts cover Run lifecycle points needed by Worker Control, the bounded active-Run descriptor used by snapshots, Attempt start and settlement for budget recovery, Tool Invocation start and settlement for external-effect recovery, and Run Budget exhaustion. Snapshot active-Run state is derived only from the committed Worker Fact projection, never from Agent live state. Facts never contain Messages, Message deltas, Tool progress, Tool arguments, Tool results, arbitrary details, or preparation status. The file journal uses a new schema version and intentionally rejects the former `worker_event` representation; no compatibility decoder or migration is retained.

Worker event routing is exhaustive and centralized. `message_start`, `message_update`, and `tool_execution_progress`, together with preparation status, are Observation-only and do not call Session persistence, Work Journal persistence, or Worker Control. Semantic Agent events first cross the narrowly typed Session seam, then append any Worker Fact, then publish their Observation, and finally invoke Worker Control when classified for it. Adding a new Agent event therefore requires an explicit routing decision at one pure classifier rather than inheriting persistence accidentally from a catch-all callback.

Fatal barrier failure is first-failure latched for the active Worker Runtime. Successfully journaled Attempt and Tool start Facts open external-effect windows; their matching settlement Facts close those windows. Failure classification is derived from those windows, including parallel Tool Invocations, rather than from a static list of event names. Cleanup after the first failure may publish best-effort Observations but must not retry the failed barrier, invoke Worker Control, or upgrade a known-safe failure because a later cleanup event has a different type. A Session failure is isolated to its Work Item. A Work Journal failure trips a Coordinator-wide persistence-failed state, rejects new work, and stops later effects across active Work Items.

Every Observation hop is non-blocking with bounded storage. Agent Observation subscribers and the per-Worker Observation Channel invoke downstream projection only from a later task. The Worker channel merges transient and post-barrier semantic events by per-Run Agent sequence; a gap or delivery overflow discards bounded process-local state and invalidates the public stream for resynchronization. Slow consumers receive the same resynchronization outcome, and failed consumers detach. Projection or serialization failure drops only the affected Observation and emits a bounded diagnostic without recursively using the failed payload. No consumer promise, presentation queue, JSON projection, evaluation, telemetry sink, or Extension is awaited by an Agent, Worker Runtime, Session barrier, Work Journal barrier, Model call, or Tool Invocation.

This decision sharpens the two-channel and Worker Control requirements of ADR-0044. It rejects filtering only token deltas at the current journal call, asynchronously queueing the same generic event behind a fatal callback, retaining an unbounded promise tail in an application projection, and reconstructing Work recovery state from full Agent events.
